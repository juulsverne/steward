## Decision proposed for review

Approve an explicit H4 hosting adjustment from App Runner to **one Amazon EC2 Linux `t3.small` in `us-west-2`, with one retained encrypted 10 GiB gp3 data volume, private Amazon S3 Standard for evidence and backups, and the existing one-agent AgentCore Runtime design**. FastAPI serves the built frontend and remains the only policy and transaction owner. This preserves SQLite and its existing local transaction semantics. It trades automatic web-host failover for a documented, tested replacement procedure, appropriate for a small judging demo with simulated settlement.

Proposed real AWS spend ceiling: **$50 incremental total for the approved deployment/evaluation/judging window**, before credits: $30 application hosting/storage/operations and final-retention allowance, $15 Bedrock/model evaluation and judging allowance, $5 AgentCore/contingency. Required judging access is **September 14 through October 8 inclusive**, approximately 600 hours/25 days; this is fixed by `docs/SUBMISSION.md` and BUILD_PLAN H6. Budget availability through the end of October 8 Pacific (October 9 at 00:00 Pacific / 02:00 Chicago), without laptop or judge-paid AWS dependencies. The amount is a proposal, not authorization or a technical billing hard stop. Owner must accept or replace the amount and approve deployment/retention/shutdown actions before provisioning or a larger paid evaluation. The seeded **$500 cleanup ledger is entirely simulated** and unrelated to AWS spend.

Material current support finding: AWS's [App Runner product notice](https://aws.amazon.com/apprunner/) says it stopped accepting new customers April 30, 2026 and does not plan new features. Existing-customer eligibility has not been checked in this account. Service availability in Oregon does not establish account eligibility. This is evidence for reconsidering the named host, not evidence that the product thesis is impossible.

### Early contract guidance delivered to B1/lead

- Retain `Store` and SQLite locally; keep policy, revisions, idempotency, ledger mutations and audit events in FastAPI transactions. Do not add a second authority in AgentCore or a web proxy.
- Evidence identity is an opaque ID plus server-owned storage key/version, SHA-256, content type, size and provenance. A deployment-local filename or temporary signed URL is not a durable evidence identity.
- Persist a pending invocation/outbox row with its triggering accepted event in the same transaction. Persist pending operator work independently of any agent session.
- Keep these boundaries independent of the eventual host. Local coding does not wait for the decision.

This App Runner option is a concrete durable-state adaptation, not a remote SQLite file share. If the owner requires **policy-bearing FastAPI itself** to stay in App Runner, the alternative is a separate RDS PostgreSQL + S3 migration: rewrite SQLite schema initialization/PRAGMAs, SQL parameters, locking and conflict handling; add transaction retry/row-lock behavior and requalify all money/concurrency tests. That is a larger, separately priced decision; this report does not approve it. An App Runner VPC connector routes application egress through the VPC and removes default public internet access, so private RDS plus Bedrock/API egress requires explicit NAT or endpoint design and extra costs. [AWS VPC connector contract](https://docs.aws.amazon.com/apprunner/latest/dg/network-vpc.html).

App Runner's [filesystem contract](https://docs.aws.amazon.com/apprunner/latest/dg/develop.html) is ephemeral. S3 synchronization of a live SQLite file cannot provide a transaction owner. SQLite WAL requires processes on the same host and is unsuitable for this shared-network-file shortcut. [SQLite WAL documentation](https://www.sqlite.org/wal.html).

## Exact proposed topology and boundaries

1. One on-demand x86 EC2 `t3.small` (2 vCPU, 2 GiB), Amazon Linux 2023, one public subnet in one chosen Oregon AZ, Internet Gateway, one Elastic IP. Set CPU-credit mode **standard** to avoid unlimited-credit surplus charges; image/agent reasoning occurs in Bedrock/AgentCore. Load-test image decoding and concurrent requests before accepting this size. No NAT gateway, ALB, RDS, EFS or autoscaling group in this topology.
2. Encrypted 20 GiB gp3 root volume for immutable application image/runtime/log buffers; encrypted **separate 10 GiB gp3 data volume**, 3,000 IOPS/125 MiB/s baseline, ext4, mounted by filesystem UUID at `/var/lib/steward`. Explicit `DeleteOnTermination=false` for data and infrastructure retention policy. Data volume attaches to exactly one instance. Container mounts this directory; API runs nonroot with one Uvicorn worker. Missing expected mount/DB causes readiness failure, never an automatic empty seed. [EBS preservation rules](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/preserving-volumes-on-termination.html).
3. Caddy HTTPS reverse proxy on that instance, loopback to FastAPI. Use an **owner-approved existing-domain subdomain** with DNS pointing to the Elastic IP and a publicly trusted certificate; no domain purchase assumed. Hostname/DNS authorization is an explicit unresolved deployment prerequisite. Configure HTTPS-only application traffic, secure cookies and trusted-proxy handling. The app remains a labeled persona sandbox, not production identity. Domain ownership/TLS automation has not been tested in this research.
4. One private, versioned S3 General Purpose bucket in Oregon with separate `evidence/`, `backups/`, and deployment artifact prefixes. SSE-S3 on objects, account/bucket Block Public Access, bucket-owner-enforced object ownership, TLS-only bucket policy. Use the AWS-managed EBS encryption key; no new customer-managed KMS key or separate audit bucket in the minimal topology. S3 objects are stored across multiple AZs; versioning permits recovery from overwrite/delete but is not an excuse for unrestricted deletion permissions. [S3 durability](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DataDurability.html), [versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html).
5. API receives uploaded bytes, validates size/type and generates a unique immutable evidence key. Successful S3 upload/checksum confirmation precedes the SQLite transaction linking ready evidence + submitted event + outbox. If DB commit fails, the object is an orphan; a bounded maintenance cleanup can remove unreferenced aged uploads after backup retention. Never acknowledge ready evidence whose bytes are only local. An S3 failure produces no accepted proof/event. Read evidence through actor-authorized API responses or short-lived signed reads; inspector loads exact stored key/version. Preserve seeded/synthetic labels.
6. API invokes the selected AgentCore Runtime endpoint via IAM and saved invocation IDs. Runtime has no DB, EBS, backup or evidence-bucket write access. It reads context and calls the same HTTPS FastAPI tools using server-to-server credentials; API loads vision bytes and calls the image model. Runtime stays public-network mode for this small demo. HTTPS callbacks use the approved origin hostname. No new autonomous agent, gateway policy engine or watching scheduler is introduced.

### IAM and network boundary

Deployment identity needs narrowly scoped creation/update permissions for the approved EC2/EBS/EIP/SG/instance profile, ECR, S3, secret, AgentCore and log resources, plus `iam:PassRole` only for their named roles. Quota, `iam:PassRole`, service-linked-role creation and inference-profile permissions must be read-only preflighted before deployment; catalog support does not prove effective account permissions.

EC2 application instance role: only configured Runtime invoke, selected image-model/profile invocation, evidence `PutObject/GetObject/GetObjectVersion`, backup `PutObject` and required prefix-scoped list/read operations, configured secret retrieval and named log writes. Runtime role: selected text-model invocation, its own log writes and its own service credential retrieval. Account/profile-specific global inference permissions must match MODEL_SELECTION; calling from Oregon does not force a global profile to remain there. Human restore/maintenance role owns volume reattachment, backup restoration and deleting expired versions; application/Runtime roles do not receive infrastructure deletion or bucket-policy administration.

Use instance/Runtime short-lived IAM credentials; require IMDSv2 and restrict application access to instance metadata as practical. Retrieve service secrets at runtime into memory/restricted files, never images, browser bundles, Git or logs. Public inbound only HTTPS 443; port 80 only certificate challenge/redirect if needed, with no application data accepted there. No public SSH; administer through Systems Manager Session Manager with a dedicated operator identity. Host outbound TLS supports AWS APIs and certificate issuance; allow required DNS. Restrict SG sources to actual consumers where stable (the judging HTTPS endpoint necessarily accepts public traffic); scope private service paths with authentication. Apply `aws:SourceAccount`/`aws:SourceArn` conditions to supported AWS-service resource-policy grants, not indiscriminately to direct instance-role requests.

Minimal operational baseline: bounded structured API/Runtime logs to CloudWatch, retained 7 days except exported acceptance receipts; default service encryption at rest; disk/backup-age/error readings and a small alarm set. Avoid recording raw uploaded bytes, tokens or hidden reasoning. **Optional hardening recommended for longer-lived use, excluded from this estimate and H1 gate:** S3 CloudTrail data events, S3 server access logs in a separate SSE-encrypted destination, customer-managed KMS encryption for CloudWatch/CloudTrail, and additional metrics/alarms. Price these explicitly before enabling them; they are not prerequisites for the small judging demo. [S3 security practices](https://docs.aws.amazon.com/AmazonS3/latest/userguide/security-best-practices.html), [EBS encryption](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-encryption.html).

## Recovery and concurrency design

`Store` currently uses `sqlite3.connect(path, timeout=10)`, per-invocation connections, foreign keys and `BEGIN IMMEDIATE`; schema version 1 contains issues/signals/source links/events. It has no uploaded-byte storage, durable delivery queue, ledger or hosted backup implementation. `Signal` currently stores `image_sha256`, not a durable object reference. `config.py` has model/region settings; `server.py` is the starter `/health` + `/ask` stream. These observations are from this checkout, not claims that later task contracts are implemented.

- Use SQLite local-file locking with short writer transactions; hold no writer lock across S3, HTTP or model calls. Keep per-request connections on their owning thread; do not share one connection across async handlers. Explicitly retain full durability (`synchronous=FULL`; WAL optional after concurrency tests). Money actions read current state, check revisions and write ledger/reservation/payment + audit + idempotency receipt in one transaction. Unique constraints protect one settlement/job/reservation effect. Bounded database-lock errors return retryable responses without partial side effects. [SQLite synchronous reference](https://www.sqlite.org/pragma.html#pragma_synchronous).
- Trigger transaction writes invocation/outbox status `PENDING`, event ID and stable invocation ID. Delivery claims a lease atomically with a fencing token/expiry, commits, then invokes Runtime outside the transaction. Runtime completion/report endpoints must match the active lease/invocation; stale callbacks cannot overwrite newer results. Retried tool calls retain stable idempotency keys, expected revisions and exact proof IDs. Delivery is at least once; business effects are idempotent, not a claimed exactly-once network delivery.
- A single event dispatcher within the API service wakes for new durable work and on startup, retries expired leases with bounded attempts/backoff, and exposes terminal delivery failure for operator review. A low-frequency retry timer may service this **saved delivery queue**; it is infrastructure recovery, not a product watching scheduler or AI polling loop. Pending human exceptions cause no inference. A crash after accepting an event but before invocation is recoverable; a crash after payment before closure reloads the persisted payment and finishes closure without paying again.
- On instance failure, fence/stop the old writer, attach the retained data volume to a replacement **in the same AZ**, mount by UUID, deploy the pinned image, validate schema/integrity, restore hostname/EIP and let the dispatcher recover pending work. RPO target: zero acknowledged DB transactions for process/container/instance replacement when the retained volume survives. RTO target: 30 minutes manual recovery, **not measured yet**. EBS is AZ-scoped and does not supply automatic multi-AZ failover. [EBS volume scope](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-volumes.html).
- Every 15 minutes and before a deployment/reset, use Python SQLite's online backup API to create a consistent snapshot file, integrity-check it, then upload to a unique S3 key with SHA-256/schema/app-version/event-watermark manifest. Do not copy only an open DB main file while ignoring its journal/WAL. Retain 24 hours of 15-minute backups plus 25 daily checkpoints; lifecycle/maintenance must expire object **versions** too. With a DB no larger than 10 MiB, these 121 retained copies consume about 1.2 GiB, leaving room for photos in the 5 GiB bucket assumption. At most 96 scheduled backup writes/day (~2,400 during judging), plus manifests/checkpoints. Growth beyond the stated size bound triggers review. [SQLite online backup](https://www.sqlite.org/backup.html).
- Before/after release, also take a quiesced data-volume EBS snapshot; stop writes and flush before snapshot, retain at most two release snapshots during judging. A block snapshot is not a demonstrated application-consistent backup until restored and checked. [AWS snapshot procedure](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-creating-snapshot.html).
- For volume/AZ loss or corruption, fence old writer, provision an empty encrypted volume in the recovery AZ, restore last validated SQLite backup, verify S3 versions/hashes for all referenced evidence, check integrity/foreign keys/ledger totals and pending invocations, then enable traffic. RPO target: at most 15 minutes **when last backup succeeded**; alarm if backup age exceeds 30 minutes. RTO target: 60 minutes manual, unmeasured. This may lose the final unbacked transactions and must be disclosed; no cross-region disaster-recovery promise. Simulated settlements are restored from the same DB snapshot as their ledger, not recomputed from a model transcript.
